COMMIT: Fix Unselected Provider Booking Count & Premature Database Creation
DATE: 2026-11-21
AUTHOR: Quick-Fix Development
MODULES AFFECTED: QUICK-FIX-BACKEND, QUICK-FIX-FRONT-END
################################################################################

1. PROBLEM IN PREVIOUS VERSION:
-------------------------------
- When a customer proceeded through the booking process (Service -> Address ->
  Provider Selection), the frontend page `ProviderSelectionPage.jsx` immediately
  fired a POST request to `/api/bookings` on component mount.
- This was done because the only backend endpoint available to find nearby
  providers (`GET /api/bookings/{bookingUniqueId}/providers`) required an existing
  `bookingUniqueId`.
- As a direct result, an incomplete booking row was inserted into the MySQL
  database with status `PENDING` and NO provider assigned (`provider_id = null`).
- If the customer left the page, closed their browser, clicked Back, or had not
  yet picked a provider, that orphan booking remained permanently in the database.
- Furthermore, the Customer Dashboard (`CustomerDashboard.jsx`), Customer Profile
  (`CustomerProfilePage.jsx`), and My Bookings page (`MyBookingsPage.jsx`) counted
  any booking with status `PENDING` toward active booking statistics.
- This caused the dashboard to display "Active Bookings: 1" and show an
  "Upcoming Booking: Home Service" card with "Quick-Fix Provider" before the user
  even finished selecting a provider.


2. HOW IT IS SOLVED NOW:
------------------------
- Added a dedicated direct provider discovery endpoint in the backend:
  `GET /api/bookings/providers?serviceUniqueId=...&latitude=...&longitude=...`
  This finds and returns eligible nearby providers using the service ID and location
  coordinates WITHOUT saving any booking to the database.
- Removed premature `bookingApi.createBooking(...)` from `ProviderSelectionPage.jsx`
  on mount. The provider list is fetched directly through the new endpoint.
- The booking in the database is ONLY created when the customer actually chooses
  a provider and clicks "Confirm Booking" on the review screen.
- Added `DRAFT` status to the `BookingStatus` enum.
- Added `providerUniqueId` to `BookingRequestModel` so that `createBooking` can
  assign the provider, calculate distance, and set status to `WAITING_FOR_PROVIDER`
  in a single atomic request.
- Added an "Exit & Discard Draft" button so users can cancel and exit cleanly.
- Updated all frontend statistics filters and backend queries to exclude `DRAFT`
  bookings and unassigned bookings (`hasProvider == false`).

COMMIT: Fix "Cannot read properties of null (reading 'toFixed')" Crash
DATE: 2026-11-21
AUTHOR: Quick-Fix Development
MODULES AFFECTED: QUICK-FIX-FRONT-END, QUICK-FIX-BACKEND
FILES CHANGED:
  1. QUICK-FIX-FRONT-END/src/components/common/StarRating.jsx
  2. QUICK-FIX-FRONT-END/src/pages/customer/ProviderSelectionPage.jsx
  3. QUICK-FIX-FRONT-END/src/components/payment/PaymentSummary.jsx
  4. QUICK-FIX-FRONT-END/src/components/payment/ReceiptModal.jsx
  5. QUICK-FIX-BACKEND/Quick-fix/src/main/java/com/example/Quick_fix/service/BookingService.java
################################################################################

1. PROBLEM IN PREVIOUS VERSION:
-------------------------------
- When opening the Provider Selection page (/customer/provider-selection),
  the page crashed with an AppErrorBoundary error:
  "This page could not load: Cannot read properties of null (reading 'toFixed')"
- Root Cause:
  1) In `BookingService.java`, `ProviderSuggestionResponseModel` had a `rating` field,
     but it was not populated during provider search, producing JSON `"rating": null`.
  2) In `StarRating.jsx`, default parameter `rating = 4.8` only triggers when
     `rating === undefined`. When `null` was passed (`rating={prov.rating}`),
     `rating` remained `null`.
  3) Executing `{rating.toFixed(1)}` on a `null` value threw:
     `TypeError: Cannot read properties of null (reading 'toFixed')`,
     triggering the React ErrorBoundary and blocking the provider list from displaying.
  4) Similar potential unhandled `.toFixed()` calls existed in `PaymentSummary.jsx`
     and `ReceiptModal.jsx` if financial fields were null or non-numeric.

2. HOW IT IS SOLVED NOW:
------------------------
- In `StarRating.jsx`, added a robust numeric guard:
  `const numericRating = Number.isFinite(Number(rating)) ? Number(rating) : 4.8;`
  and formatted using `numericRating.toFixed(1)`.
- In `ProviderSelectionPage.jsx`, safeguarded rating props:
  `rating={prov.rating || 4.8}` and `rating={bookingDraft.provider?.rating || 4.8}`.
- In `PaymentSummary.jsx` and `ReceiptModal.jsx`, wrapped amounts in
  `(Number(val) || 0).toFixed(2)` to protect against nulls.
- In `BookingService.java`, explicitly populated `response.setRating(4.8)` on
  all suggested providers so the backend returns valid ratings.

COMMIT: Enforce 30 km Maximum Radius for Nearby Provider Discovery & Booking
DATE: 2026-11-21
AUTHOR: Quick-Fix Development
MODULES AFFECTED: QUICK-FIX-BACKEND, QUICK-FIX-FRONT-END
FILES CHANGED:
  1. QUICK-FIX-BACKEND/Quick-fix/src/main/java/com/example/Quick_fix/service/BookingService.java
  2. QUICK-FIX-BACKEND/Quick-fix/src/main/java/com/example/Quick_fix/controller/BookingController.java
  3. QUICK-FIX-FRONT-END/src/api/bookingApi.js
  4. QUICK-FIX-FRONT-END/src/pages/customer/ProviderSelectionPage.jsx
################################################################################

1. PROBLEM IN PREVIOUS VERSION:
-------------------------------
- The provider discovery logic did not enforce any maximum distance radius filter.
- Any provider in the entire database offering the service was returned, even if
  they were 200+ km away (e.g. 278.09 km away from a Coimbatore customer).
- Customers could unintentionally book distant providers across different cities,
  resulting in unrealistic travel distances and charges.

2. HOW IT IS SOLVED NOW:
------------------------
- Added a strict 30.0 km maximum distance cutoff (`DEFAULT_MAX_DISTANCE_KM = 30.0`)
  in `BookingService.java`.
- Provider discovery endpoints and search algorithms now discard any provider whose
  distance exceeds 30.0 km (`if (distance > maxDistanceKm) continue;`).
- Added server-side validation in `createBooking` and `selectProvider` rejecting any
  attempt to book a provider located beyond 30 km.
- In `ProviderSelectionPage.jsx`, added client-side filtering (`<= 30 km`) and
  updated UI text to "Showing verified providers within 30 km".
- If no providers exist within 30 km, the system clearly informs the user:
  "No eligible providers found within 30 km of your selected address."

COMMIT: Fix 400 Bad Request on Provider Mark En-Route & Data Truncation
DATE: 2026-11-21
AUTHOR: Quick-Fix Development
MODULES AFFECTED: QUICK-FIX-BACKEND, DATABASE (quickfixfinal)
################################################################################

1. PROBLEM IN PREVIOUS VERSION:
-------------------------------
- On the Provider Active Service page (`/provider/active-service/:uniqueId`), when the
  provider clicked the "Mark En Route (Travelling to Site)" button:
  A PUT request was sent to `/api/bookings/{bookingUniqueId}/en-route`.
- The request immediately failed with HTTP 400 Bad Request:
  `"message": "could not execute statement [Data truncation: Data too long for column 'status' at row 1] [update booking set ... where id=?]"`
- Root Cause:
  In the MySQL database (`quickfixfinal`), the `status` column in table `booking` was
  defined as a MySQL ENUM:
  `status enum('COMPLETED','CONFIRMED','CUSTOMER_CANCELLED','IN_PROGRESS','PENDING','PROVIDER_ACCEPTED','PROVIDER_CANCELLED','PROVIDER_REJECTED','PROVIDER_SELECTED','WAITING_FOR_PROVIDER')`
- The enum values `PROVIDER_EN_ROUTE`, `DRAFT`, and `DISPUTED` (which exist in Java's `BookingStatus` enum)
  were MISSING from the MySQL column definition.
- When Hibernate executed `UPDATE booking SET status='PROVIDER_EN_ROUTE' WHERE id=?`, MySQL rejected it
  with a Data Truncation error.
- Similarly, `booking.payment_status` was constrained to `enum('FAILED','PAID','PENDING','REFUNDED')`,
  missing values from Java `PaymentStatus` (e.g. `SUCCESS`, `CREATED`, `REFUND_PENDING`, `PARTIALLY_REFUNDED`).
- In addition, in `BookingService.java`, `startBooking` strictly checked `if (booking.getStatus() != BookingStatus.CONFIRMED)`,
  which would prevent starting a service once marked as `PROVIDER_EN_ROUTE`.


2. HOW IT IS SOLVED NOW:
------------------------
- In MySQL Database (`quickfixfinal`):
  Modified the `booking.status` and `booking.payment_status` columns to `VARCHAR(40) NOT NULL`:
  `ALTER TABLE booking MODIFY COLUMN status VARCHAR(40) NOT NULL;`
  `ALTER TABLE booking MODIFY COLUMN payment_status VARCHAR(40) NOT NULL;`
  This aligns with JPA's standard `@Enumerated(EnumType.STRING)` mapping and eliminates MySQL enum
  data truncation errors permanently.
- In `BookingService.java`:
  Updated `startBooking` to accept bookings that are either `CONFIRMED` or `PROVIDER_EN_ROUTE`:
  `if (booking.getStatus() != BookingStatus.CONFIRMED && booking.getStatus() != BookingStatus.PROVIDER_EN_ROUTE)`
- Verified endpoint `PUT /api/bookings/494646/en-route`:
  The request executed with HTTP 200 OK and updated status to `PROVIDER_EN_ROUTE`.

COMMIT: Payment Module Optimization, Cash on Delivery & Order Query Fix
DATE: 2026-11-21
AUTHOR: Quick-Fix Development
MODULES AFFECTED: QUICK-FIX-BACKEND, QUICK-FIX-FRONT-END, DATABASE (quickfixfinal)
################################################################################

1. PROBLEMS IN PREVIOUS VERSION:
-------------------------------
PROBLEM A: Missing `created_at` in MySQL Payment Table Causing SQL Exception on Order Creation
- In `PaymentRepository.java`:
  `findFirstByBooking_UniqueIdAndStatusInOrderByCreatedAtDesc(...)` generated SQL:
  `SELECT ... FROM payment WHERE ... ORDER BY created_at DESC`.
- The MySQL `payment` table did NOT have a `created_at` column because `BaseEntity`
  lacked `@MappedSuperclass`.
- When `paymentService.createOrder` attempted to reuse or lookup existing orders, Hibernate
  threw `SQLGrammarException: Unknown column 'created_at' in 'order clause'`.

PROBLEM B: Lack of Doorstep / Cash Payment Option
- The UI promised: "* No upfront payment required. Pay directly after service completion via Cash or UPI."
- However, the payment module only supported Razorpay checkout. There was no explicit
  Cash on Delivery (COD) settlement endpoint to record payments collected in cash by technicians,
  leaving bookings stuck in `PENDING` payment status if paid in cash.

PROBLEM C: Lambda Variable Capture Error in BookingService
- In `selectProvider`, variable `booking` was modified after being referenced inside a stream
  lambda expression, triggering a Java compilation error:
  `local variables referenced from a lambda expression must be final or effectively final`.


2. HOW IT IS SOLVED NOW:
------------------------
SOLUTION A: Database Schema & Repository Query Fix
- In `PaymentRepository.java`:
  Changed query method to `findFirstByBooking_UniqueIdAndStatusInOrderByIdDesc(...)`.
  Since `id` is the auto-increment primary key, sorting by `id DESC` accurately retrieves
  the latest order without relying on an unindexed or missing timestamp column.
- In MySQL Database (`quickfixfinal`):
  Added `created_at` column: `ALTER TABLE payment ADD COLUMN created_at DATETIME DEFAULT CURRENT_TIMESTAMP;`
- In `PaymentEntity.java`:
  Explicitly declared `@Column(name = "created_at") private LocalDateTime createdAt = LocalDateTime.now();`
  ensuring receipt generation has accurate server timestamps.

SOLUTION B: Cash Payment Settlement (Doorstep Cash / Cash on Delivery)
- In Backend (`QUICK-FIX-BACKEND`):
  - Created `CashPaymentRequestModel.java`.
  - Added `recordCashPayment` in `PaymentService.java` and `PaymentController.java` (`POST /api/payments/cash`).
  - Records a verified `PaymentEntity` with `paymentMethod = "CASH"` and status `PAID`.
  - Automatically transitions `booking.paymentStatus` to `PAID` and credits provider earnings.
- In Frontend (`QUICK-FIX-FRONT-END`):
  - Added `paymentApi.recordCashPayment(bookingUniqueId, customerUniqueId)` in `paymentApi.js`.
  - Added "Pay Cash Directly to Technician" button with confirmation prompt on `BookingPaymentPage.jsx`.
  - Directly redirects customer to verified payment receipt upon cash confirmation.

SOLUTION C: Final Variable Capture Fix
- In `BookingService.java`:
  Extracted `final ServiceType targetServiceType = booking.getService().getServiceType();`
  prior to the stream filter lambda, ensuring full Java 17 compilation compliance.
